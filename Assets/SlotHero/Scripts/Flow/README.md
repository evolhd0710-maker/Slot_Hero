# Slot Hero 흐름 코드

화면을 이어 주는 곳이다.
타이틀에서 프로필로, 런으로, 맵에서 방으로, 런 종료 결과로 넘긴다.

화면 하나하나는 자기 일만 알고 다음에 무엇이 오는지는 모른다.
그것을 아는 것은 `GameFlowController` 뿐이다. 화면들이 서로를 부르지 않게 하려는 것이다.

저장 시스템 기획서 v0.1 / 08 저장 시점 의 네 자리를 부르는 것도 여기 일이다.

## 파일 구성

```
Flow/
  Runtime/
    Data/
      GameScreen.cs          지금 어느 화면인지
      RunContext.cs          런 하나를 화면들이 쓰는 꼴로 바꿔 준다
      ICombatEntry.cs        전투로 넘기고 결과를 받는 창구
    Config/
      RunCatalogConfig.cs    문양·코인·유물 목록. 임시다
      RunEventConfig.cs      이벤트 목록. 임시다
      EventScripts.cs        이벤트 기획서의 각본을 옮긴 것
      RewardRuleConfig.cs    방 종류마다 보상 골드와 카드 장수. 임시다
    RunCatalog.cs            IMerchantCatalog 구현
    RunClock.cs              플레이 시간. 런 시간을 재는 곳은 이것 하나다
    RunSession.cs            런을 열고 닫는다. 새로 시작, 이어하기, 유물 순서 저장, 끝내기
    RunResultMaker.cs        끝난 런을 결과 화면 자료로 바꾼다
    RoomRewardFlow.cs        방 보상 정산. 전투 골드 쌓기, 보상 남김, 한 번에 받기
    RewardMaker.cs           방의 보상을 시드로 정한다
    EventRoomFlow.cs         이벤트 방 진행. 각본 고르기, 선택지, 전투 왕복, 전투에 넘길 조건
    RunEventWorld.cs         이벤트 작업을 런에 건다
    MapPeekFlow.cs           방 안에서 지도를 잠깐 띄우고 걷는다. 지도 버튼을 켤지 정한다
    OwnedLimitFlow.cs        코인과 유물의 소지 한도. 버릴 것 고르기 창의 요청을 만든다
    FlowPopups.cs            흐름이 띄우는 확인과 알림 팝업의 글과 버튼
    ItemDetailTexts.cs       아이템 상세 오버레이의 글
    PlaceholderCombatEntry.cs  전투 대역. 전투가 오면 뗀다
    GameFlowController.cs    전체 흐름. 화면을 넘기고 위의 것들을 잇는다
```

## 흐름 조종기를 나눴다

2026년 10월 8일에 `GameFlowController` 에서 책임 다섯을 떼어 냈다.
외부 검토가 "저장·복구, 이벤트 선택, 보상 처리 책임을 조금씩 분리하라" 고 권했고 원재가 하라고 했다.
같은 날 원재가 지도 버튼과 팝업 처리도 나누라고 해 둘을 더 뗐다.
한 파일에서 함께 판단해야 하는 상태가 많아 고치다 다른 것을 건드리기 쉬웠다.

| 떼어 낸 것 | 맡는 일 | 들고 있는 상태 |
| --- | --- | --- |
| `RunSession` | 런 시작, 이어하기(늘 파일에서 다시 읽는다), 유물 순서 저장, 런 종료 | 진행 중인 런(`RunContext`), 유물 순서 |
| `RoomRewardFlow` | 전투 골드와 오버킬 쌓기, 이벤트 전투의 보상 고르기 횟수 쌓기, 방 보상 정하기, 보상 남김 표시, 한 번에 받기 | 런 데이터의 보상 칸(`RewardPending`, `RewardCombatGold`, `RewardOverkillGold`, `RewardCardRounds`, `RewardCardRoundsTaken`)에 적는다 |
| `EventRoomFlow` | 각본 고르기, 선택지 처리, 고르기 화면 내용, 전투를 연 선택지로 돌아오기, 전투에 넘길 조건(`CombatOptions`) | 돌고 있는 각본, 돌아올 선택지, 보상 두 배, 부정 효과 |
| `MapPeekFlow` | 지도 버튼을 켤지, 방 안에서 지도를 띄우고 걷기, 버튼 모양 맞추기 | 지도를 잠깐 띄웠는지 |
| `FlowPopups` | 프로필 지우기, 새 게임, 런 종료, 게임 끄기, 설정 기본값 복원 같은 확인 팝업과 저장 실패 같은 알림 팝업 | 팝업이 떠 있는지만 팝업 쪽에서 읽는다 |

다섯 다 화면 흐름을 모른다. 화면을 열고 닫고 다음 화면으로 넘기는 일은 `GameFlowController` 에 남았다.
팝업 버튼을 눌렀을 때 할 일은 조종기가 넘긴다. 그래서 `FlowPopups` 는 글과 버튼만 안다.
다섯은 일반 클래스라 유니티 없이 `검증/FlowTests.cs` 에서 바로 굴려 본다.
설정 에셋 연결은 조종기에 그대로 두어 씬을 다시 묶지 않아도 된다. 조종기가 `Awake` 에서 다섯을 만든다.

## 한 씬에서 켜고 끈다

씬을 갈아 끼우지 않는다.
설정과 팝업과 현재 빌드가 다른 화면 **위에** 겹쳐 떠야 하기 때문이다.
씬으로 나누면 그 셋을 얹을 자리가 없다.

`GameScreen` 에 그 셋이 없는 것도 같은 까닭이다.
그것들은 어느 화면 위에서든 열리고 닫으면 원래 화면으로 돌아간다.

저장소 코드는 씬을 갈아 끼운다.
전투를 붙일 때 전투만 따로 씬으로 두고 additive 로 얹는 길이 남아 있다.

## 화면이 이어지는 차례

```
타이틀 ──새 게임/이어하기──> 맵
  │ 현재 프로필 버튼                │ 방을 고르면 · 자동 저장 ② 방 진입
  └─> 프로필 선택 ──고르면──> 타이틀 │
                                  성소 / 이벤트 / 전투
                                    │ 방을 끝내면 · 자동 저장 ③ 방 완료
                                  보상 ──받으면──> 맵
                                    │            보스 방이면 다음 스테이지 맵
                                    │
               쓰러지거나 마지막 스테이지의 보스를 깨면
                                    └──> 런 종료 결과 ──타이틀로──> 타이틀
```

게임을 켜면 쓸 수 있는 프로필이 있을 때 타이틀부터 연다. 프로필이 하나도 없을 때만 프로필 선택부터 연다.
성소는 보상 화면을 거치지 않고 맵으로 간다. 받을 것이 있는 방만 보상 화면을 연다.
단계마다 무엇이 일어나는지는 피그마 순서도 ① ~ ⑨ 에 그렸다.

방 종류가 어느 화면으로 가는지는 `RoomTypes.IsCombat` 이 가른다.
성소와 이벤트는 각자 화면으로, 나머지(일반·엘리트·보스)는 전투로 간다.

## 08 저장 시점을 부르는 자리

| 시점 | 부르는 곳 |
| --- | --- |
| 런 시작 | `StartNewRun` → `RunSession.StartNew`. 시작 아이템과 유물 순서를 넣은 뒤 한 번 쓴다 |
| 방 진입 | `EnterRoom` |
| 방 완료 | `ClearRoom`. 방을 나올 때 보상을 정한 뒤 부른다 |
| 런 종료 | `EndRun` → `RunSession.End`. 완료 기록을 쓴 뒤 런을 지운다 |
| 설정 변경 | `HandleSettingChanged` |

네 자리 밖에서 런 데이터를 쓰는 곳은 셋이다.

| 때 | 부르는 곳 |
| --- | --- |
| 보상을 받았다 | `HandleRewardReceived` → `RoomRewardFlow.Receive`. 골드와 카드를 넣고 한 번 쓴다 |
| 다음 스테이지로 넘어갔다 | `AdvanceStage` 가 `SaveService.OnStageAdvanced` 를 부른다 |
| 방 밖에서 저장하고 나가기 | `HandleEndRunConfirmClosed`. 맵과 보상 화면에서 지금 상태를 쓴다 |

방 완료는 같은 방에서 두 번 불려도 한 번만 세어진다.
화면을 정리하는 길이 여럿이라 두 번 불릴 수 있기 때문이다.
그 막음은 `SaveService.OnRoomCleared` 안에 있다.

## 런 시간과 일시정지

RunClock 이 런 시간을 센다. **런 시간을 재는 곳은 이것 하나다.**
상단 표시줄은 흐름이 매 프레임 넘기는 값을 보여 주기만 하고, 초가 바뀔 때만 글자를 고친다.
예전에는 표시줄에도 시계가 있어 둘이 따로 흘렀고 매 프레임 글자를 새로 만들었다. 2026년 10월 8일에 하나로 모았다.
실제로 흐른 시간(`Time.unscaledDeltaTime`)을 센다. 연출 속도를 `Time.timeScale` 로 바꿔도 빨라지지 않는다.

**설정 화면이 떠 있을 때만 멈춘다**(`GameFlowController.IsClockPaused`).
현재 빌드, 잠깐 띄운 지도, 고르기 화면, 팝업은 모두 시간이 흐른다.
2026년 10월 6일 원재가 "팝업 때도 시간이 흘러야 하고 설정 화면 때만 멈춘다" 고 정했다.
예전에는 현재 빌드, 고르기 화면, 팝업에서도 멈췄다.

## 지도 버튼과 현재 빌드 버튼

둘은 띄우는 화면만 다르고 움직임이 같다. 지금 화면 위에 띄우고, 진행을 바꾸지 않고, 닫으면 보던 화면으로 돌아간다.
하나가 떠 있을 때 다른 버튼을 누르면 떠 있던 것을 걷고 그것을 띄운다.
예전에는 지도를 띄운 위에서 현재 빌드를 누르면 지도 위에 겹쳐 열렸다. 2026년 10월 6일에 같게 고쳤다.

다른 점은 둘이다. 지도 버튼은 방 안(보상 화면 포함)과 현재 빌드가 떠 있을 때 켜진다. 다음 방을 고르는 맵에는 지도가 이미 떠 있기 때문이다.
맵 화면에서 현재 빌드를 띄운 채 지도 버튼을 누르면 현재 빌드만 닫힌다.
현재 빌드 버튼은 화면이 떠 있는 동안 감춘다. `Hud/README.md` 에서 물어서 정한 것이다.

**멈출지 말지는 매 프레임 지금 열려 있는 화면을 읽어 정한다.**
여는 자리와 닫는 자리를 하나하나 이으면 한 군데만 빠뜨려도 시계가 영영 멈춰 있는다.

Time.timeScale 은 건드리지 않는다.
연출과 스크롤까지 함께 멈추면 겹쳐 뜬 화면 자체가 뻣뻣해지기 때문이다.

## ESC

ESC 는 겹쳐 뜬 화면이 있으면 **그쪽이 먼저 가져간다.**
설정과 현재 빌드 화면은 각자 자기 ESC 를 다루므로 흐름은 건드리지 않는다.

겹쳐 뜬 것이 없으면 흐름이 설정을 연다.
프로필 선택 화면에서는 열지 않는다. 그 앞이 없어 나갈 길이 헷갈리기 때문이다.

## RunContext 가 자료를 한쪽으로 모은다

저장에 실리는 값은 `RunSaveData` 하나뿐이다.
그런데 화면마다 받는 꼴이 다르다.

| 화면 | 받는 것 |
| --- | --- |
| 성소 | `IPlayerVitals`, `RunGoldState`, `IMerchantCatalog`, `RunRelicPool` |
| 현재 빌드 · 런 종료 결과 | `CurrentBuildSnapshot` |
| 상단 표시줄 | 체력과 골드 숫자 |

화면마다 자료를 따로 들고 있으면 저장된 값과 어긋난다.
`RunContext` 가 한쪽으로만 흐르게 묶는다. 진짜 값은 늘 `RunSaveData` 쪽이다.

성소가 `RunGoldState` 를 직접 건드려도 `Changed` 를 타고 런 데이터가 따라온다.
그때 쓴 만큼은 통계의 소모 골드로도 쌓인다.

## 전투는 창구로만 주고받는다

전투 코드는 아직 붙지 않았다.
흐름이 전투를 직접 부르면 나중에 전투가 올 때 흐름을 뜯어야 하므로
`ICombatEntry` 로만 주고받는다.

지금은 `PlaceholderCombatEntry` 가 대신 선다.
전투 방에 들어가면 팝업을 띄워 이겼는지 졌는지를 직접 고르게 한다.
그래야 맵과 저장과 런 종료 결과까지 실제로 이어지는지 볼 수 있다.

**게임 자료가 아니다.** 전투가 오면 이 컴포넌트를 떼고 진짜 것을 붙인다.

## 코인과 유물의 소지 한도

전투 시스템 기획서가 "유물은 소지하는 갯수에 제한이 있다" 고 정했고,
전투 UI 기획서 stt 와 인게임 화면 기획서 13 이 코인 최대 5개, 유물 최대 6개로 적었다.
가득 찼을 때 어떻게 할지와 한도가 바뀌는 것은 2026년 10월 9일 원재가 정했다.

**한도는 런마다 저장한다**(`RunOwnedData.CoinCapacity`, `RelicCapacity`). 조건에 따라 바뀔 수 있어서다.
시작 값은 `RunCatalogConfig.StartingCoinCapacity`(5)와 `StartingRelicCapacity`(6)이고 `RunCatalog.Attach` 가 채운다.
한도 칸이 생기기 전에 저장한 런은 초기값 -1(정하지 않음)이 남아 이때 시작 값이 들어간다. 현재 빌드 화면의 칸 수도 이 한도를 따른다.

**가득 찬 채로 얻으면 버릴 것 고르기 창을 띄운다.** 고르기 화면을 그대로 쓰고 요청은 `OwnedLimitFlow` 가 만든다.
고르면 그것을 버리고 새것을 받고, "포기" 를 누르면 받지 않는다. 버린 것은 바로 사라진다. 골드로 바꿔 주지 않는다(2026년 10월 9일 원재).
런을 시작할 때 주는 물건은 한도를 따로 보지 않는다. 원재가 그럴 필요 없다고 정했다.

| 얻는 곳 | 묻는 때 | 포기하면 |
| --- | --- | --- |
| 보상 화면 | 카드를 고르고 받기를 누를 때(`RewardScreenController.CanReceive`) | 보상 화면에 남는다. 다른 카드나 건너뛰기를 고를 수 있다 |
| 행상 | 사기 전(`PurchaseResult.NoRoom`, `SanctumController.RoomNeeded`) | 사지 않는다. 골드도 그대로다 |
| 이벤트 | 선택지를 고를 때(`EventRoomFlow.TryGetRoomNeed`) | 선택지를 고르지 않은 것으로 하고 화면에 남는다 |

이벤트에서 고를 수 있는 것이 가득 찬 획득뿐이면 떠나는 선택지를 끼운다. 포기한 뒤 나갈 길이다.
26 반짝이는 것 의 보석 고르기처럼 받기뿐인 화면이 그렇다.
12 잠든 보물 의 둘 다 가진다 는 유물 둘을 받으므로 모자란 만큼 차례로 고른다. 도중에 포기하면 아무것도 버리지 않는다.
바꾸는 작업(13 유물 교환, 20 환전, 25, 27)은 하나를 내주고 하나를 받으므로 묻지 않는다.

**한도가 줄어 넘치면 넘친 만큼 바로 버리게 한다**(`GameFlowController.ResolveOverflow`). 이때는 포기 버튼이 없고 ESC 도 받지 않는다.
한도를 바꾸는 창구는 `RunContext.ChangeCoinCapacity` · `ChangeRelicCapacity` 와 이벤트 작업 `ChangeCoinCapacity` · `ChangeRelicCapacity` 다.
한도는 0 까지 내려간다(2026년 10월 9일 원재). 0 이면 그 물건을 가질 수 없고, 얻으려 하면 버릴 칸 없는 고르기 창이 떠 포기만 할 수 있다.
그래서 "아직 정하지 않음" 은 0 이 아니라 -1 로 둔다. **어떤 조건에서 바뀌는지는 아직 없다.** 유물이나 이벤트 기획서가 오면 이 창구를 부르게 붙인다.

런 데이터에 넣는 곳(`RunCatalog.Acquire`, `RoomRewardFlow.Receive`, `RunEventWorld` 의 받기)도 한도를 넘기지 않게 한 번 더 막는다.

## 이벤트가 연 전투

이벤트 기획서 3장 도전 이벤트 공통 규칙 을 따른다. 35 도전자 와 38 매복 이 전투를 연다.

전투를 열 때 `CombatOptions` 를 함께 넘긴다. 방 전투는 `CombatOptions.None` 이다.

| 칸 | 뜻 |
| --- | --- |
| `FromEvent` | 이벤트가 연 전투다. 이기면 이벤트 마무리 화면으로 돌아가고 보상은 방을 나갈 때 받는다 |
| `DoubleReward` | 이기면 보상 두 배. 35 도전자 |
| `PenaltyId`, `PenaltyText` | 걸 부정 효과. 3장 목록 D1 ~ D6 가운데 하나 |

**부정 효과.** 목록은 `RunEventConfig.CombatPenalties` 에 있고 기본값은 3장 의 여섯 가지다.
35 도전자 는 화면 2 에서 목록의 서로 다른 둘을 A 와 B 로 내놓고, 고른 것을 기억해 두었다가 화면 3 의 전투에 건다.
38 매복 은 싸울 때 목록에서 하나를 무작위로 뽑는다.
효과를 실제로 거는 일과 "해당 전투가 끝나면 해제된다" 는 전투의 몫이다. 지금은 전투 대역 팝업에 무엇이 걸렸는지 적기만 한다.

**보상 두 배.** 기획서가 "전투 골드 보상이 2배가 된다. 전투 후 보상 선택(문양, 유물 등)을 2회 진행한다" 고 정했다.
이벤트 방은 방 규칙에 카드가 없으므로 이벤트 전투를 이기면 보상 고르기 횟수를 따로 쌓는다(`RewardCardRounds`).
매복은 한 번, 도전자는 두 번이다. 카드는 `RewardRuleConfig.EventCombatCardsLike` 방(지금은 일반 방)의 카드 규칙으로 뽑는다.
첫 고르기에 두 배가 된 전투 골드가 함께 나오고, 두 번째 고르기는 카드만 있다.
고르기마다 시드와 방과 차례로 카드를 정하므로 두 번째 고르기 앞에서 꺼졌다 이어도 같은 카드가 뜬다.

예전에는 각본이 부정 효과를 고르게만 하고 전투에 넘기지 않았고, 보상 두 배는 골드에만 걸렸다.
2026년 10월 8일 외부 검토가 짚어 이었다.

## 스테이지별 등장 범위와 희귀도 분포

2026년 10월 9일 외부 검토가 권했고 원재가 **틀만 만들기로** 정했다. 기획서에 수치가 없고 스테이지도 아직 하나라 기본값은 모두 "따지지 않음" 이다.
기본값에서는 예전과 같은 보상, 진열, 이벤트가 나온다. 수치는 에디터에서 넣는다.

| 칸 | 자리 | 쓰는 곳 |
| --- | --- | --- |
| 이벤트의 등장 스테이지와 출현 비중 | `EventScript.MinStage`, `MaxStage`, `Weight` | `RunEventConfig.Pick` |
| 문양, 코인, 유물의 등장 스테이지 | `SymbolDefinition`, `ItemDefinition` 의 `MinStage`, `MaxStage` | 보상 카드(`RewardMaker`), 행상 후보와 문양 변경(`RunCatalog.Collect…`) |
| 보상의 스테이지별 희귀도 분포 | `RewardRuleConfig.RarityByStage` | `RewardMaker.AddCards` |
| 행상의 스테이지별 희귀도 분포 | `SanctumConfig.RarityByStage` | 코인 진열과 유물 순서(`MerchantStockBuilder`, `RunRelicPool.Draw`) |

- 스테이지 범위는 0 이하면 따지지 않는다(`StageRange`). 칸이 없던 예전 에셋도 0 으로 읽혀 모든 스테이지에 나온다
- 희귀도 분포는 스테이지 범위마다 한 줄이고, 일반부터 전설까지 다섯 칸의 비중이다(`StageRarityWeights`).
  덮는 줄이 없으면 고르게 뽑는다. 있으면 장마다 등급부터 굴리고 그 등급 안에서 고르게 뽑는다(`RarityPicker`)
- 문양은 등급이 없다. 보상 카드에 문양이 섞이면 분포를 쓰지 않는다
- 행상 유물은 분포가 있으면 등급만 굴리고, 순서 테이블에 남은 것 가운데 그 등급에서 차례가 가장 앞선 것을 꺼낸다. 같은 등급 안에서는 테이블 순서를 지킨다
- 이벤트가 주는 무작위 문양, 코인, 유물에는 아이템의 등장 스테이지를 아직 쓰지 않는다. 남은 일에 적었다

## 물건 목록 조회 색인

실행 중 이름, 그림, 문양 태그, 코인·유물 등급을 찾을 때는 `RunCatalogConfig` 안의 색인(식별자 → 목록 자리)을 쓴다.
에디터가 고치는 것은 그대로 목록이다. 목록 길이가 바뀌거나 에디터에서 값을 고치면(`OnValidate`) 다시 만들고,
찾은 자리의 식별자가 다르면 그 자리에서 다시 만든다. 코드에서 목록 안의 식별자를 바꾸면 `InvalidateIndex` 를 부른다.
같은 식별자가 여럿이면 예전처럼 문양, 코인, 유물 차례로 먼저 나온 것을 쓴다.

보상 후보는 물건 목록의 자리로만 담고 고른 것만 카드로 만든다. 이벤트의 등급 비중 뽑기는 후보의 등급과 등급별 수를 한 번만 센다.
둘 다 난수 차례와 후보 차례가 예전과 같아 같은 시드면 예전과 같은 결과가 나온다. 순수 검사가 예전 방식을 옮겨 두고 견준다.
2026년 10월 9일 외부 검토가 권했다.

## 코인과 유물의 획득 경로

2026년 10월 9일 원재가 "특정 이벤트에서만 등장, 행상에서만 등장, 행상에서 미등장 등을 구분할 장치를 넣어 달라. 다른 경우도 추가될 수 있다" 고 했다.
물건마다 두 칸을 둔다. 기본값은 모든 경로에서 나온다.

- `ItemDefinition.ExcludedFrom` 이 경로로는 나오지 않는다. 보상, 행상, 이벤트를 함께 고를 수 있다(`ItemSource`)
- `ItemDefinition.OnlyInEvents` 비어 있지 않으면 이벤트로는 여기 적은 이벤트에서만 나온다

| 하고 싶은 것 | 고르는 값 |
| --- | --- |
| 행상에서 미등장 | `ExcludedFrom` = 행상 |
| 행상에서만 등장 | `ExcludedFrom` = 보상 + 이벤트 |
| 특정 이벤트에서만 등장 | `ExcludedFrom` = 보상 + 행상, `OnlyInEvents` = 그 이벤트 |

거르는 자리는 보상 카드(`RewardMaker`), 행상 진열과 유물 새로고침(`RunCatalog.CollectCoinCandidates`, `CollectRelicCandidates`),
이벤트가 무작위로 주거나 바꿔 주는 후보(`RunEventWorld`)다. 이벤트가 연 전투의 보상 카드는 보상으로 친다. 시작 아이템은 거르지 않는다.
경로가 늘면 `ItemSource` 에 값을 더하고 그 경로가 후보를 모으는 자리에서 `ItemDefinition.CanComeFrom` 으로 거른다.

## 이벤트는 한 런에 한 번

같은 런에서는 같은 이벤트를 다시 보지 않는다. 2026년 10월 9일 원재가 정했다.
이벤트 방에서 이벤트가 정해지면 런 데이터의 `SeenEventIds` 에 적고, 다음 이벤트 방은 그 목록을 빼고 뽑는다(`RunEventConfig.Pick`).
목록은 방 완료 저장에 실린다. 방 안에서 나갔다 이어 하면 방에 들어갈 때의 목록으로 다시 뽑아 같은 이벤트가 나온다.
스테이지를 넘겨도 비우지 않는다. 이벤트를 다 만나면 그 뒤 이벤트 방은 이벤트 없이 끝난다.

## 임시인 것

`RunCatalogConfig` 와 `RunEventConfig` 는 **임시다.**

저장소의 `SymbolData` `RelicData` `BetCoinData` 에셋과
이벤트 기획서의 실제 이벤트가 오면 갈아 끼운다.
그 자료가 아직 없어서 게임이 한 바퀴 돌지 못하므로 같은 모양의 자리만 먼저 만들어 둔 것이다.
거기 적힌 이름과 값은 게임 수치가 아니다.

문양은 저장소 규칙대로 서로 다른 태그를 둘 가진다.

## 붙이는 법

### 1. 확인용 씬을 먼저 만든다

메뉴 `Slot Hero / 확인용 씬 만들기 / 모두 다시 만들기`.

게임 씬은 화면을 새로 짓지 않는다. 확인용 씬에서 만들어 둔 것을 그대로 옮겨 온다.
화면 만드는 코드를 두 벌 두면 한쪽만 고쳐져 어긋나기 때문이다.

### 2. 설정 에셋을 만든다

메뉴 `Slot Hero / 설정 에셋 한 번에 만들기`.

물건 목록(`RunCatalogConfig`)과 이벤트 목록(`RunEventConfig`)은 **없을 때만 만들고 이미 있으면 덮지 않는다.** 만든 뒤에는 에디터의 에셋이 원본이다.
2026년 10월 9일 외부 검토가 권했고 원재가 정했다. 예전에는 돌릴 때마다 이벤트를 코드의 각본으로 갈아 끼우고, 물건 목록의 기획서 수치를 덮었다.
코드의 값으로 되돌릴 때만 아래 메뉴를 누른다. 에디터에서 고친 것은 사라진다.

- `Slot Hero / 이벤트 목록을 코드 각본으로 되돌리기`
- `Slot Hero / 물건 목록 수치를 기획서 값으로 되돌리기` 태그 가치, 시작 골드, 덱 최소 장수, 코인과 유물 소지 한도

### 3. 게임 씬을 만든다

메뉴 `Slot Hero / 게임 씬 만들기`.

`Assets/SlotHeroScenes/게임.unity` 가 생기고 빌드 설정의 첫 자리에 들어간다.
플레이를 누르면 타이틀 화면부터 시작한다.

### 4. 굴려 본다

메뉴 `Slot Hero / 게임 씬 굴려 보기`.

플레이 모드로 들어가지 않고 흐름을 손으로 밀어 본다.
저장은 메모리에만 한다. 진짜 저장 파일을 건드리지 않는다.

## 검증 결과

유니티 없이 순수 로직만 따로 빌드해 229건을 확인했고 전부 통과했다.

- 떼어 낸 것을 직접 굴린다. `RunSession` 은 시작 아이템과 유물 순서를 넣고 열고, 파일에서 다시 읽어 유물 자리를 잇고,
  끝내면 런을 놓는다. `RoomRewardFlow` 는 전투 골드를 바로 주지 않고 쌓으며(도전 전투는 두 배), 성소에는 보상을 주지 않고,
  받으면 골드와 카드를 한 번에 넣고 보상 칸을 비운다. `EventRoomFlow` 는 같은 방이면 같은 이벤트를 열고,
  전투를 연 선택지로 돌아오며, 놓으면 보상 두 배까지 지운다. `MapPeekFlow` 는 런이 없거나 방 밖이면 버튼을 끈다
- 이벤트 전투의 보상. 도전자는 고르기 두 번(두 번째는 카드만, 첫 번째와 다른 카드, 이어해도 같은 카드), 매복은 한 번이다
- 소지 한도. 시작 값 5 · 6, 예전 런은 시작 값으로 채우기, 가득 차면 넣지 않기, 버릴 것 고르기 요청(포기 가능, 고른 것 빼기), 한도 바꾸기와 넘침
- 경제 수치가 기획서와 같다. 태그 가치 1 · 1 · 2 · 2 · 3 · 3 · 4 · 4 · 5, 문양 값 예시 30 · 40 · 55 · 65, 시작 골드 0
- 방 종류 여섯이 모두 이름을 가지고 전투인지 아닌지 갈린다
- 상단 표시줄이 보이는 화면과 아닌 화면이 갈린다
- 행상 후보에서 이미 가진 코인과 유물이 빠지고 문양은 빠지지 않는다
- 유물 테이블은 보유 여부를 따지지 않고 전부 담는다
- 산 물건이 런에 들어가고 문양 변경이 하나를 빼고 하나를 넣는다
- 성소가 골드를 건드리면 런 데이터와 통계가 함께 움직인다
- 체력이 `IPlayerVitals` 로 오간다
- 빌드 스냅샷의 태그 합이 문양 장수의 두 배다
- 같은 시드와 같은 방이면 같은 이벤트가 나온다

유니티에서는 게임 씬을 굴려 577건을 확인했고 전부 통과했다. 흐름에 걸린 것은 다음과 같다.

- 게임을 켜면 프로필 선택이 열리고 프로필을 고르면 타이틀로 간다
- 런을 시작하면 맵이 열리고 런 파일이 쓰이고 이어하기가 켜진다
- 성소와 이벤트와 전투 방에 들어갔다 나오면 맵으로 돌아온다
- 방 진입과 방 완료가 저장되고 지나온 방이 한 번씩만 세어진다
- 런을 끝내면 런 파일이 지워지고 메타가 누적된다
- 다시 읽은 런의 시드와 골드가 같고 이어한 맵의 시드도 같다
- 35 도전자 를 끝까지 하면 고른 부정 효과가 전투에 넘어가고, 이긴 뒤 마무리 화면으로 돌아가며,
  방을 나갈 때 보상 화면이 두 번 뜬다. 두 번째 앞에서 이어 해도 그 화면이 다시 뜬다
- 소지 한도가 차면 행상과 보상에서 버릴 것 고르기가 뜨고, 포기하면 사지도 받지도 않으며, 고르면 버리고 얻는다.
  한도가 줄어 넘치면 닫을 수 없는 고르기가 떠 넘친 만큼 버리게 한다

## 기획서에 없어 내가 정한 부분

- **게임을 켜면 마지막으로 논 프로필의 타이틀부터.** 저장 쪽이 첫 프로필을 미리 만들어 둔다.
  프로필은 타이틀의 현재 프로필 버튼으로 바꾼다
- **런 시드는 시계에서 뽑는다.** 시드 자체는 매번 달라야 한다.
  뽑은 뒤에는 같은 시드가 어느 기기에서든 같은 결과를 낸다
- **마지막 스테이지의 보스를 깨면 런을 깬 것.** 스테이지 수는 `_stageCount` 이고 지금은 1 이다.
  다른 스테이지의 보스는 보상을 받은 뒤 다음 스테이지 맵으로 넘어간다(2026년 10월 6일 원재)
- **런 포기와 저장하고 나가기.** 상단 표시줄의 런 종료 버튼이 세 갈래를 준다

## 남은 일

- **전투.** 창구 `ICombatEntry` 와 대역 `PlaceholderCombatEntry` 가 선다.
  부정 효과 D1 ~ D6 를 얼마나 세게 걸지는 전투가 붙을 때 정한다. 창구로는 이미 넘긴다(`CombatOptions`)
- **런 시작 선택 화면.** 저장소의 `SlotHero.RunStart` 가 그 일을 하는데
  필요한 에셋이 오면 붙인다. 지금은 설정 에셋의 시작 물건을 그대로 준다
- **2스테이지 이후.** 스테이지 넘기기는 돈다. 2스테이지 맵 설정값과 스테이지 수가 정해지면 `_stageCount` 를 올린다
