# Slot Hero 저장 코드

저장 시스템 기획서 v0.1 을 옮긴 것이다.
런 데이터와 메타 데이터와 설정 데이터 셋을 파일로 읽고 쓴다.

화면을 모른다. 자료와 파일만 다룬다.
어느 화면이 언제 저장을 부르는지는 `Flow` 가 정한다.

## 파일 구성

```
Save/
  Runtime/
    Data/
      RunSaveData.cs         진행 중인 런 하나 (05장)
      RunStatusData.cs       체력과 골드와 흐른 시간
      RunOwnedData.cs        문양 풀, 유물, 코인
      RunStatisticsData.cs   이번 런의 통계
      RelicPoolSaveData.cs   유물 순서를 어디까지 꺼냈는지
      MetaSaveData.cs        해금, 도전과제, 누적 통계, 지난 런 기록 (06장)
      SettingsSaveData.cs    기기 설정 (07장)
      SaveChecksum.cs        유효성 검사 값
      AutoSavePoint.cs       자동 저장 시점 (08장)
      SaveOutcome.cs         읽고 쓴 결과와 팝업 여부 (10장)
    Config/
      SaveConfig.cs          프로필 수와 파일 이름. ScriptableObject
    Storage/
      ISaveStorage.cs        글 하나를 이름 하나에 넣고 빼는 창구
      FileSaveStorage.cs     진짜 파일
      MemorySaveStorage.cs   메모리. 검증에 쓴다
      SaveRepository.cs      읽고 쓰기와 예외 처리
    SaveService.cs           자동 저장 시점을 실제로 부르는 창구. MonoBehaviour
```

| 기획서 | 코드 |

| 05 런 데이터 · 구성 개요 | `RunSaveData` |

| 05 · 런 통계 | `RunStatisticsData` |

| 06 메타 데이터 | `MetaSaveData` |

| 07 로컬 환경 설정 | `SettingsSaveData`. 항목은 `Settings` 영역의 `SettingsValues` |

## 저장하지 않는 값

기획서 10쪽이 정한 대로다.

- **시드에서 다시 만드는 값** 맵 구조, 방 타입, 몬스터 패턴, 보상 후보, 행상 재고.
  런 시드만 저장하고 나머지는 열 때마다 다시 만든다
- **초기화되는 값** 방 안에서 진행 중이던 것. 방에 들어간 시점으로 돌아간다
- **다시 계산해서 얻는 값** 저장된 값에서 나오는 것

그래서 `RunSaveData` 에 맵이 통째로 들어가지 않는다. 시드와 지나온 방 번호만 있다.

## 시드로 다시 만들 수 없어 저장하는 값

2026년 10월 5일에 원재가 정했다.

- **유물을 어디까지 꺼냈는지** `RelicPool`. 순서 자체는 시드와 테이블 번호로 다시 만들 수 있다.
  그런데 어디까지 꺼냈는지는 성소에 몇 번 들렀고 새로고침을 몇 번 했는지에 달려 시드로는 알 수 없다.
  저장하지 않으면 이어할 때 처음부터 다시 꺼내 이미 본 유물이 또 나온다.
  첫 테이블을 다 쓰고 두 번째 테이블로 넘어간 뒤도 같다. 테이블 번호와 꺼낸 자리를 함께 저장한다.
  순서도 담는다. 한 진열에 같은 유물이 두 번 오르지 않게 하느라 꺼내는 도중에 순서를 미루는 일이 있어서다
- **이번 런에서 만난 이벤트** `SeenEventIds`. 같은 런에서 같은 이벤트를 다시 보지 않게 한다(2026년 10월 9일 원재).
  어느 방에서 무엇을 만났는지는 앞 방들의 선택에 달려 시드만으로는 알 수 없다. 방 완료 저장에 실린다
- **보상을 아직 받지 않았는지** `RewardPending`.
  보상 내용은 시드와 방에서 다시 만든다. 받기 전에 나갔는지만 적어 이어할 때 그 방의 보상 화면에서 시작한다.
  모든 보상은 받을 때 한 번에 받으므로(2026년 10월 6일 원재) 반쯤 받은 상태가 없다.
  예전의 "골드를 이미 받았는지" 칸 `RewardGoldGranted` 는 그래서 지웠다. 예전 파일에 남아 있어도 읽을 때 버린다
- **그 보상의 오버킬 골드** `RewardOverkillGold`. 2026년 10월 6일에 원재가 정했다.
  기본 골드와 카드는 시드에서 다시 나오지만 오버킬은 전투에서 얼마나 넘치게 때렸는지에서 나와 시드로 알 수 없다.
  전투를 이기면 적고 방 완료 저장에 함께 실린다. 보상을 받거나 다음 방에 들어가면 0 으로 돌아간다
- **보상에 합칠 전투 골드** `RewardCombatGold`. 2026년 10월 6일에 원재가 정했다.
  전투에서 얻은 골드는 이기는 순간 주지 않고 보상의 기본 골드에 더해 받을 때 한 번에 준다.
  전투가 정한 값이라 시드로 다시 만들 수 없어 오버킬과 같이 저장한다. 도전 이벤트가 연 전투면 두 배가 된 값이 들어 있다
- **코인과 유물의 소지 한도** `RunOwnedData.CoinCapacity`, `RelicCapacity`. 2026년 10월 9일에 원재가 정했다.
  조건에 따라 바뀔 수 있어 런마다 적는다. 0 까지 내려갈 수 있어 정하지 않음은 -1 로 둔다. 칸이 생기기 전의 파일은 초기값 -1 이 남아 런을 열 때 설정의 시작 값(5, 6)이 들어간다

유물 순서는 흐름이 쓰기 직전에 옮겨 담는다. `SaveService.RunSaving` 이 쓰는 자리마다 알린다.
성소 상태는 저장하지 않는다. 위 "초기화되는 값" 그대로 방에 들어간 시점으로 돌아간다.

## 런 시드 하나에서 갈라 쓰는 난수

저장하는 난수 값은 **런 시드 하나**(`RunSaveData.Seed`)뿐이다. 런을 시작할 때 시계에서 한 번 뽑는다.
쓰는 곳마다 이 시드에 자리 번호를 섞어 따로 난수를 만든다. 자리 번호가 같으면 늘 같은 값이 나온다.

| 쓰는 곳 | 섞는 것 | 코드 |
| --- | --- | --- |
| 맵 | 스테이지 번호, 다시 만든 횟수 | `MapRandom.ForStage` |
| 이벤트 고르기 | 방 번호 | `RunEventConfig.Pick` |
| 이벤트 안의 무작위 | 방 번호 | `EventRandom.ForEvent` |
| 보상 | 노드 번호, 스테이지 번호 | `RewardMaker.Make` |
| 행상 진열과 문양 변경 | 방 번호. 그 뒤로는 상태를 이어 굴린다 | `SanctumRandom.ForSanctum` |
| 유물 순서 | 테이블 번호. **어디까지 꺼냈는지는 저장한다** | `SanctumRandom.ForRelicPool` |

방 번호는 스테이지와 노드 번호를 섞은 값이다(`GameFlowController.RoomKey`).
그래서 몇 번째로 들어왔는지, 이어하기를 몇 번 했는지와 상관없이 같은 방이면 같은 결과가 나온다.

## 이어하기는 늘 파일에서 읽는다

`GameFlowController.ContinueRun` 은 먼저 `SaveService.ReloadRun` 으로 런을 파일에서 다시 읽는다.
방 안에서 "저장하고 나가기" 를 하고 끄지 않은 채 바로 이어 하면 메모리에는 방 안에서 바뀐 런이 남아 있다.
예전에는 그것으로 이어 해서 방 안에서 얻은 골드가 남았고, 방에 다시 들어가며 그 값이 파일에도 써졌다.
2026년 10월 6일 원재가 "저장 후 이어하기를 해도 모든 상황이 같게 나와야 한다" 고 정해 고쳤다.
`CheckGameScene.CheckContinueRepeatsRoom` 이 성소와 이벤트에서 처음, 바로 이어 하기, 다시 읽어 이어 하기 셋을 견준다.

**플레이 시간도 저장한 시점의 값을 따른다.** 2026년 10월 7일 원재가 정했다.
이어 하면 런 데이터의 `ElapsedSeconds` 에서 다시 흐른다. 저장 뒤에 진행한 시간은 더하지 않는다.
방 안에서 저장하고 나가면 방에 들어갈 때의 값으로 돌아가고, 프로필의 누적 플레이 시간도 런이 끝날 때 이 값으로 쌓인다.
`CheckGameScene.CheckContinueInsideRoom` 이 확인한다.

## 현재 방을 번호로 적는다

기획서는 "스테이지 내 현재 위치하는 방의 그리드 좌표"라고 적었다.
코드는 맵 노드 번호를 대신 쓴다.

노드 번호가 시드에서 똑같이 다시 나오고 단계와 줄을 그대로 가리키기 때문이다.
좌표를 따로 적으면 맵을 다시 만들 때 노드와 맞춰 보는 일이 한 겹 더 늘어난다.
**기획서와 다른 자리다.** 좌표로 적어야 하는 까닭이 생기면 바꾼다.

## 저장 형식의 판 번호

세 자료가 모두 `FormatVersion` 을 가진다. 지금 판은 `SaveFormat.Current` = 1 이다.

**판 번호는 저장할 때 적기만 하고 읽을 때는 보지 않는다.**
2026년 10월 8일 원재가 "버전 작성은 유지하되 그거에 영향을 받지 않게" 하라고 정했다.
업데이트를 해도 저장 형식이 늘 바뀌는 것은 아니고 게임을 옛 판으로 되돌릴 일도 없다.

| 읽은 판 | 하는 일 |
| --- | --- |
| 지금 판, 더 낮은 판, 더 높은 판 | 모두 똑같이 읽는다. 판 때문에 지우거나 다시 쓰지 않는다 |

예전에는 판 번호로 갈렸다. 더 높은 판은 읽지 않았고, 더 낮은 판은 `SaveMigration` 으로 올려 읽었으며
올리는 걸음이 없는 판이면 그 런을 버렸다. 그러면 업데이트에서 판만 올리고 걸음을 빠뜨렸을 때 멀쩡한 저장이 날아간다.
`SaveMigration` 과 `Upgraded`, `TooNew` 결과를 모두 뺐다.

자료 구조를 고쳐도 대개는 손댈 것이 없다.

- 파일에 없는 칸은 `JsonUtility` 가 기본값으로 두고 읽는다. 업데이트로 칸을 더한 경우다
- 이 게임이 모르는 칸은 버리고 읽는다. 칸을 뺀 경우다
- 체크섬은 파일에 적힌 글 그대로 확인하므로 칸이 늘거나 줄어도 걸리지 않는다. 아래 "체크섬" 참고

**칸의 뜻을 바꿀 때만 조심한다.** 같은 이름에 다른 뜻을 담으면 옛 값이 새 뜻으로 읽힌다.
그때는 이름을 새로 짓는다. 설정의 연출 속도를 `effectSpeed` 에서 `presentationSpeed` 로 바꾼 것이 그 예다.

## 체크섬

FNV-1a 32비트다. 8자리 열여섯 진수로 적는다.

암호가 아니다. 파일이 잘리거나 손으로 고쳐진 것을 잡아내는 용도다.
매길 때는 체크섬 칸을 비우고 JSON 으로 만든 뒤 그 글을 줄인다.

**읽을 때는 파일에 적힌 글에서 체크섬 칸만 다시 비워 줄인다** (`SaveChecksum.VerifyJson`).
그러면 매길 때의 글이 그대로 나온다.

예전에는 읽은 자료를 다시 JSON 으로 만들어 줄였다. 그런데 업데이트로 칸이 하나만 늘어도
다시 만든 글에 그 칸이 끼어 값이 달라졌고, 멀쩡한 런이 손상으로 처리되어 지워졌다.
2026년 10월 8일에 바꿨다. 이미 저장된 파일도 그대로 통과한다. 디스크의 실제 파일 셋으로 확인했다.
곱셈과 xor 뿐이라 어느 기기에서든 같은 값이 나온다.

## 쓰다 꺼져도 남는다

`ISaveStorage.Write` 는 임시 이름에 먼저 쓰고 다 쓴 뒤에 본 이름으로 바꿔 단다.
**바꿔 달 때 기존 파일을 지우지 않는다.** `FileSaveStorage` 는 `File.Replace` 로 한 번에 갈아 끼우고,
그것을 지원하지 않는 곳에서만 기존 파일 위에 덮어 복사한다. 다 쓴 임시 파일은 바꿔 달기에 실패해도 남겨 둔다.

게임을 켤 때 `SaveRepository.CleanTempFiles()` 가 남은 임시 파일을 치운다.

| 남은 모양 | 하는 일 |
| --- | --- |
| 본 파일이 온전하다 | 임시 파일을 지우고 본 파일을 쓴다. 10 예외 처리 의 "임시 파일 삭제 후 기존 저장 데이터 사용" 이다 |
| 본 파일이 없거나 망가졌고 임시 파일은 온전하다 | 임시 파일을 본 파일로 되살린다. 실패하면 임시 파일을 그대로 두고 다음에 켤 때 다시 해 본다 |
| 둘 다 온전하지 않다 | 임시 파일을 지운다 |

온전한지는 체크섬으로 본다.

**되살릴 때는 글을 다시 쓰지 않고 이름만 바꿔 단다**(`ISaveStorage.Promote`).
예전에는 같은 글을 `Write` 로 다시 썼는데, 그 쓰기의 임시 이름이 지금 되살리려는 파일과 같았다.
쓰기가 실패하면 반쯤 쓴 임시 파일로 보고 지워, 본 파일이 없을 때는 유일한 진행까지 사라졌다.
2026년 10월 9일 외부 검토가 실제 파일로 재현했다. 검사도 같은 상황(다른 쪽이 임시 파일을 열어 둔 채 바꿔 달기 실패)을 만들어 본다.

**되살리지 못한 사이에도 그 임시 파일을 본 파일처럼 다룬다.** 같은 날 다시 검토하며 막았다.

- 읽기: 본 파일이 없거나 망가졌고 온전한 임시 파일이 남았으면 그것을 읽는다(`ReadSaved`). 본 파일이 온전하면 늘 본 파일이다
  **본 파일이 있는데 읽지 못하면 임시 파일로 대신하지 않는다.** 본 파일이 잠긴 채 쓰기가 실패하면 다 쓴 임시 파일이 남는데, 그것은 실패한 쓰기라 본 파일이 정본이다.
  예전에는 런 종료 저장이 그렇게 실패한 뒤 이어하기를 하면 임시 메타의 "런 없음, 기록 있음" 을 읽어 런을 지웠고, 잠금이 풀리면 기록도 없었다.
  읽지 못하는 동안에는 읽기 실패로 알리고 메타와 런을 맞추지도 않는다(`ReconcileRunFlag`). 2026년 10월 9일 외부 검토가 재현했다
- 런 파일이 있는지 볼 때도 그 임시 파일을 센다. 안 그러면 메타의 "런 있음" 을 내리고,
  다음 실행에서 되살리기가 성공해도 메타와 어긋난 런 파일로 보고 지운다
- 쓰기: 그 이름에 새로 쓰기 전에 먼저 되살려 본다. 안 되면 쓰지 않고 쓰기 실패를 알린다. 새로 쓰면 같은 임시 이름을 덮기 때문이다
- 런이나 프로필을 지울 때는 임시 파일도 함께 지운다. 남기면 본 파일 대신 읽혀 끝난 런이 되살아난다

**읽지 못한 것과 망가진 것을 나눈다.** 파일이 있는데 글을 읽지 못했으면 잠시 막힌 것으로 보고 손대지 않는다.
예전에는 읽지 못한 임시 파일을 망가진 것으로 보고 지워 유일한 진행이 사라졌다. 본 파일을 읽지 못했을 때도 그 위에 임시 파일을 덮지 않는다.
2026년 10월 9일 외부 검토가 실제 파일로 재현했다. 검사는 다른 쪽이 읽기를 막고 지우기만 허락한 채 파일을 붙잡는 상황을 만든다.

같은 날 다시 받은 검토로 임시 파일 정리 밖에서도 같은 규칙을 지키게 했다. 읽지 못한 것은 결과 `SaveOutcome.ReadFailed` 로 따로 알린다.

| 읽지 못한 것 | 하지 않는 것 | 대신 하는 것 |
| --- | --- | --- |
| 본 메타나 백업 | 곧바로 백업으로 되돌리기, 새 프로필로 초기화 | `LoadMeta` 가 null 과 읽기 실패를 돌려준다. 프로필을 고르지 않는다 |
| 런 파일이나 남은 런 임시 파일 | 손상으로 지우기, 메타의 "런 있음" 맞추기 | 런 파일이 있는 것으로 본다. 타이틀은 이어하기만 끈다(`SavedRunState.Unreadable`) |
| 설정 | 손상으로 기본값 되돌림 알림, 기본값으로 파일 덮어쓰기 | 이번에는 기본값으로 쓰고 다시 읽히면 바꾼 항목만 얹는다(아래 "설정을 읽지 못했을 때") |

**기다렸다 다시 읽는다.** 백신 검사나 동기화 프로그램이 파일을 붙잡는 일은 오래 걸릴 수 있어 바로 실패로 끝내지 않는다.
흐름이 "저장 파일을 기다리는 중" 팝업을 띄우고 `SaveConfig.ReadRetryDelaySeconds`(5초)마다 `ReadRetryCount`(6번) 다시 읽는다(`Flow/ReadRetry`).
읽히면 팝업을 거두고 하려던 일을 마저 한다. 팝업의 그만두기를 누르면 기다리기를 멈추고 아무것도 고치지 않는다.
2026년 10월 9일 원재가 "팝업을 띄운 후 여유를 두고 재시도" 하라고 정했다. 다시 읽는 자리는 셋이다.

- 게임을 켤 때 읽지 못하는 프로필이나 설정이 있으면 기다린 뒤에 들어갈 프로필을 고른다.
  여기서 다 기다리고 포기하거나 그만두면 바로 이어지는 타이틀에서는 같은 파일을 다시 기다리지 않고 이어하기만 꺼 둔다
- **본 메타가 온전하면 백업이 잠겨 있어도 읽을 수 있는 것으로 본다**(`CannotReadMeta`). 백업은 본 메타가 망가졌을 때만 쓴다.
  예전에는 백업만 잠겨도 30초를 기다리고 실패 팝업을 띄웠다(2026년 10월 9일 전체 검토)
- 프로필을 고를 때. 읽지 못한 칸을 눌러도 같다
- 타이틀에서 저장된 런이나 메타를 읽지 못할 때. 이어하기를 눌렀다가 못 읽었으면 다시 읽히는 대로 이어 한다

기다리는 동안의 읽기 실패는 저장 창구가 따로 알리지 않는다. 기다리는 팝업 위에 실패 팝업이 겹치기 때문이다.

**끝내 못 읽으면 백업으로 되살린다. 백업과 런이 온전할 때만이다**(`SaveRepository.RestoreUnreadableMeta`).
되살린 메타에 그 런을 이어 붙여 "런 있음" 을 켜고 런 횟수를 그 런 번호까지 올린 뒤 본 자리에 써 본다.
본 파일이 아직 잠겨 쓰지 못해도 되살린 메타로 들어가고, 다음 메타 저장이 다시 쓴다.
런이 없으면 되살리지 않는다. 백업은 한 번 앞의 값이라 마지막 런 기록이 빠져 있을 수 있어 그것으로 덮으면 기록을 잃는다.
그때는 읽지 못했다고 알리고 그대로 둔다. 2026년 10월 9일 원재가 "백업이 있고 런이 정상이면 메타를 복원하고 런과 연결해 검증한다" 고 정했다.

**본 메타가 망가져 백업으로 되살릴 때도 런을 이어 붙인다**(`LinkIntactRun`). 런을 시작하면 백업은 시작 전 메타라 "런 없음" 이 적혀 있다.
예전에는 그 백업이 되살아난 뒤 메타와 런을 맞추는 단계가 멀쩡한 런을 지웠다.
**이미 끝난 런은 붙이지 않는다.** 메타의 지난 런 기록에 그 런 번호가 있으면 기록을 쓰고 런 파일을 지우기 전에 꺼져 남은 것이다.
붙이면 그 런을 다시 하고 기록이 두 번 쌓인다. 그 파일은 맞추는 단계가 지운다.
**런을 잠시 못 읽으면 백업으로 되살리지도, 새로 만들지도 않는다.** 런을 붙일 수 없는 채 확정하면 "런 없음" 이 본 자리에 남고,
런이 다시 읽힐 때 맞추는 단계가 멀쩡한 런을 지운다. 망가진 본 파일을 그대로 두고 읽기 실패로 돌려준다. 2026년 10월 9일 외부 검토.

읽지 못하는 임시 메타나 백업만 남은 프로필도 있는 것으로 본다(`ProfileExists`). 빈 자리로 보이면 다시 읽기로 이어지지 않고 그 위에 새 프로필을 만들 수 있었다.

이어하기에서 메타를 다시 읽다 막히면 런을 놓는다. 그때 타이틀은 손상이 아니라 읽지 못함(`SavedRunState.Unreadable`)이다.
예전에는 런을 놓은 것만 보고 손상으로 알려, 손상 알림이 권하는 새 게임으로 멀쩡한 런이 지워질 수 있었다.

프로필 목록에서는 읽지 못한 칸을 손상 칸과 같이 들어갈 수 없게 두되(`ProfileSummary.IsReadFailed`),
누르면 삭제를 권하지 않고 기다렸다 다시 읽어 들어간다. 이름을 몰라 기본 이름을 적는다. 비워 두면 빈 자리로 보여 그 위에 새 프로필을 만들 수 있다.
읽지 못한 프로필의 이름은 바꾸지 않는다. 새로 만든 메타로 덮으면 기록을 잃는다.
예전에는 잠시 읽지 못한 프로필이 "프로필1 · 0초" 로 덮였고 잠금을 풀어도 돌아오지 않았다.

**2026년 10월 8일 외부 검토에서 받은 지적으로 고쳤다.** 예전에는 기존 파일을 지우고 나서 임시 파일을 옮겨,
그 사이에 꺼지면 기존 파일이 사라졌고 남은 임시 파일마저 다음에 켤 때 지워 진행을 통째로 잃을 수 있었다.

## 메타 쓰기가 실패하면 다시 쓴다

**메타는 런보다 중요하다.** 2026년 10월 9일 원재가 "런 데이터 손실은 비교적 작은 문제지만 메타 손상은 작지 않은 문제" 라고 했다.

- **런 시작은 메타를 먼저 쓰고 런을 쓴다.** 그 사이에 꺼지면 "런 있음" 인데 런 파일이 없는 모양이 남아, 프로필을 고를 때 적힌 값만 내린다.
  거꾸로면 "런 없음" 인데 런 파일이 남아 그 런을 지운다
- **지금 프로필의 메타 쓰기가 실패하면 기억해 두고**(`_metaPending`) 다음에 런을 저장할 때마다 메타부터 다시 쓴다.
  예전에는 런 시작에 메타 쓰기가 한 번 실패하면 같은 날 다시 쓰지 않아, 다음에 켤 때 맞추는 단계가 그날 한 런을 통째로 지웠다.
  외부 검토가 짚었다
- 같은 프로필을 다시 읽을 때(이어하기)도 먼저 써 본다. 그래도 못 쓰면 파일의 옛 메타를 읽어 들이지 않고 메모리의 메타를 그대로 두되,
  **런은 파일에서 다시 읽는다.** 옛 메타를 읽으면 "런 없음" 때문에 런이 지워지고 런 횟수도 되돌아간다.
  런까지 메모리의 것을 쓰면 방 안에서 쓴 골드나 채운 체력을 들고 방에 다시 들어간다. 추가 외부 검토가 짚었다
- 다른 프로필로 옮길 때도 먼저 써 본다. 끝내 못 쓰고 옮겨 밀린 메타를 놓쳐도 다음에 그 프로필을 고를 때 런이 지워지지 않는다(아래)
- 런 종료가 기록을 다 쓰면 다시 쓸 것이 없다

**메타가 모르는 런은 지우지 않고 이어 붙인다**(`ReconcileRunFlag`). 메타는 "런 없음" 인데 온전한 런 파일이 있을 때
그 런 번호가 메타의 런 횟수보다 크고 지난 런 기록에도 없으면, 런을 시작한 뒤 메타 쓰기가 실패해 메타만 뒤처진 것이다.
지우지 않고 "런 있음" 과 런 횟수를 맞춰 메타를 쓴다. 잃은 것이 없으므로 알림은 띄우지 않는다.
끝낸 런(기록에 있다)이나 버린 런(번호를 이미 셌다)이 남은 것이면 예전처럼 지우고 알린다.

## 설정을 읽지 못했을 때

설정 파일을 잠시 읽지 못하면 이번에는 기본값으로 시작하되 **파일을 덮어쓰지 않는다**(`SaveService.IsSettingsUnread`).
지금 값이 기본값에서 시작했으므로 그대로 쓰면 바꾸지 않은 항목까지 기본값으로 덮여 기존 설정이 사라진다. 2026년 10월 9일 추가 외부 검토.

- 게임을 켤 때 프로필과 함께 기다렸다 다시 읽는다. 끝내 못 읽으면 읽지 못했다고 알린다
- 그 사이에 바꾼 항목은 적어 두고, 바꿀 때마다와 설정 화면을 열 때 다시 읽어 본다(`TryRecoverSettings`).
  읽히면 파일의 값 위에 바꾼 항목만 얹어 쓰고 설정 화면을 다시 그린다
- 아직 못 읽으면 이번 변경은 이번 실행에서만 쓰고, 저장하지 못했다는 알림을 한 번만 띄운다

## 런 종료와 프로필 읽기의 순서

같은 검토에서 받은 지적 셋도 고쳤다.

**런 종료는 완료 기록을 먼저 쓰고 런을 지운다.** `EndRun(cleared, today, out saved)` 이다.

- 기록 쓰기가 실패하면 런 파일과 메모리의 런을 그대로 두고, 메모리의 메타를 쓰기 전으로 되돌린 뒤 `saved` 를 false 로 돌려준다.
  쓰기 실패 팝업을 띄우고 런 종료 저장 알림은 띄우지 않는다. 다시 끝내도 기록은 한 번만 쌓인다
- 기록을 쓰고 런 파일을 지우기 전에 꺼지면 메타는 "런 없음" 인데 런 파일이 남는다.
  다음에 프로필을 고를 때 `ReconcileRunFlag` 가 그 파일을 지운다. 기록은 이미 한 번 쌓였으므로 다시 세지 않는다
- 예전에는 런을 먼저 지우고 기록을 써, 기록 쓰기가 실패하면 진행도 기록도 잃고 저장 알림까지 떴다

**프로필을 고를 때는 메타와 런 파일을 먼저 맞추고 런을 읽는다.**
예전에는 런을 먼저 읽어, 위의 경우 파일은 지워도 메모리에 런이 남아 이어하기가 켜졌다.

**백업만 남은 프로필도 있는 프로필로 본다.** `ProfileExists` 가 본 파일과 백업을 함께 본다. 되살리지 못하고 남은 온전한 임시 메타나 임시 백업도 센다(10월 9일).
예전에는 빈 칸으로 보여 백업 복구까지 가지 못했고, 첫 프로필 만들기가 그 자리를 새 이름으로 덮을 수도 있었다.
목록을 만들다 백업으로 되살리면 팝업을 띄운다.

## 붙이는 법

### 1. 설정 에셋을 만든다

메뉴 `Slot Hero / 설정 에셋 한 번에 만들기` 를 누르면
`Assets/SlotHeroConfigs/Save/SaveConfig.asset` 이 생긴다.

### 2. 씬에 놓는다

빈 오브젝트에 `SaveService` 를 붙이고 `_config` 에 위 에셋을 넣는다.
`_initializeOnAwake` 를 켜 두면 게임을 켤 때 저장 폴더를 열고 임시 파일을 치운다.

저장 자리는 `Application.persistentDataPath` 아래 `SlotHero` 폴더다.

### 3. 호출

```csharp
save.SelectProfile(0);                 // 메타와 런을 읽는다
RunSaveData run = save.StartRun(seed, r => GiveStartingItems(r)); // 런 시작. 채운 뒤 한 번 쓴다
save.OnRoomEntered(nodeId);            // 방 진입
save.OnRoomCleared();                  // 방 완료
save.EndRun(cleared, "2026-09-23", out bool saved); // 런 종료. 기록을 못 쓰면 saved 가 false 이고 런은 남는다
```

팝업이 필요한 일이 생기면 `NoticeRequested` 로 알려 준다.
자동 저장 안내를 띄울 자리는 `Saved` 로 알려 준다.

## 테스트하다 저장을 되돌리는 법

**저장 파일은 유니티 프로젝트 밖에 쌓인다.**
`Application.persistentDataPath` 아래의 `SaveConfig.FolderName` 폴더다.
윈도에서는 이렇게 된다.

```
C:\Users\<사용자>\AppData\LocalLow\<회사>\<게임>\SlotHero
```

그래서 프로젝트를 지우거나 다시 받아도 저장은 그대로 남는다.
테스트하다 처음부터 다시 해 보려면 그 폴더를 비워야 한다.

손으로 찾아가지 않게 메뉴를 만들어 뒀다. `Slot Hero / 저장 데이터` 다.

| 메뉴 | 무엇 |
| --- | --- |
| 폴더 열기 | 탐색기로 그 자리를 연다 |
| 무엇이 있는지 보기 | 지우지 않고 파일 목록만 콘솔에 적는다 |
| 전부 지우기 | 프로필 셋과 설정이 다 사라진다. 처음 켠 상태가 된다 |
| 진행 중인 런만 지우기 | 프로필과 설정은 두고 런만 지운다 |

지우기 둘은 묻고 나서 지운다. 되돌릴 수 없기 때문이다.
명령줄에서 부를 때는 물을 사람이 없어 묻지 않고 지운다.

```
unity run <프로젝트> -- -executeMethod SlotHero.ToolsEditor.ClearSaveData.ClearAll
```

**런만 지울 때는 메타의 "저장된 런이 있다" 표시도 함께 내린다.**
안 내리면 메타는 런이 있다는데 파일이 없어 타이틀이 **런 데이터 손상**으로 읽는다.
백업 메타까지 내린다. 백업만 남아 있으면 되살아날 때 도로 손상으로 읽힌다.

| 무엇 | 파일 | 프로필마다 |
| --- | --- | --- |
| 런 데이터 | `profile{번호}_run.json` | 따로 |
| 메타 데이터 | `profile{번호}_meta.json` | 따로 |
| 메타 백업 | `profile{번호}_meta.backup.json` | 따로 |
| 설정 | `settings.json` | **기기당 하나.** 번호가 안 붙는다 |

저장 시스템 기획서 v0.1 의 "프로필 3개, 프로필당 런 데이터 1 + 메타 데이터 1,
설정은 기기당 1" 그대로다.

확인한 것은 이렇다.

- 셋에 서로 다른 이름과 골드와 문양을 넣고 다시 읽어도 섞이지 않는다
- 한 프로필의 런만 지우면 그 프로필의 런만 없어지고 메타는 남는다
- 프로필을 통째로 지우면 그 자리의 런과 메타와 백업만 사라지고 나머지 둘은 멀쩡하다
- 프로필을 다 지워도 설정은 남는다. 기기당 하나이기 때문이다
- 런과 메타와 백업과 설정의 파일 이름이 서로 겹치지 않는다

**런에는 백업이 없다.** 메타만 백업을 둔다.
기획서가 "불러오기 실패 시 백업 데이터 사용"을 메타에만 적어 두었고,
런은 망가지면 버리고 새로 시작하는 쪽으로 정했기 때문이다.

## 검증 결과

유니티 없이 순수 로직만 따로 빌드해 300건을 확인했고 전부 통과했다.

- 런과 메타가 JsonUtility 로 그대로 오간다. 한글 이름과 날짜도 온전하다
- 같은 값이면 같은 체크섬이 나오고, 파일 글에서 골드를 한 자리만 고쳐도 걸린다
- 빈 체크섬과 체크섬 칸이 없는 파일은 통과시키지 않는다. 이름에 체크섬처럼 보이는 글이 있어도 진짜 칸을 찾는다
- 판 번호가 더 낮아도, 더 높아도 그대로 읽고 지우거나 다시 쓰지 않는다. 메타와 설정도 같다
- 업데이트로 칸이 늘어난 경우(옛 파일에 칸이 없음)와 줄어든 경우(모르는 칸이 있음) 모두 읽힌다
- 더 높은 판 메타와 런이 함께 있어도 런 기록 맞추기가 런 파일을 지우지 않는다
- 체력이 최대를 넘거나 들어가지 않은 방을 깼다고 하면 앞뒤가 안 맞는 것으로 본다
- 같은 문양을 두 번 넣으면 합쳐지고 0장이 되면 목록에서 빠진다
- 도전과제는 목표에 닿을 때 한 번만 달성되고 날짜가 남는다
- 지난 런 기록은 스무 개까지 남고 최신 것이 앞에 온다

**10 예외 처리 표의 줄을 하나씩 실제로 재현해 본다.**

- 파일이 없으면 새 프로필과 저장 데이터와 백업을 만든다
- 메타가 망가지면 백업으로 읽고 본 자리에 되돌려 둔다. 팝업을 띄운다
- 메타와 백업이 둘 다 망가지면 프로필을 초기화한다. 팝업을 띄운다
- 런이 망가지거나 체크섬이 틀리면 지우고 진행하지 않은 것으로 친다. 팝업을 띄운다(확인 하나, 2026년 10월 7일 원재)
- 메타가 말하는 런 존재 여부와 실제 파일이 어긋나면 한쪽에 맞춰 고친다. 팝업을 띄운다
- 설정이 망가지면 전부 기본값으로 되돌린다. 팝업은 띄우지 않는다
- 쓰기에 실패하면 알리고 기존 저장 데이터가 그대로 남는다
- 쓰다 꺼져 남은 임시 파일을 치우고 나면 기존 값이 그대로다

**2026년 10월 8일 외부 검토에서 받은 저장 오류 넷을 재현해 본다.**

- 본 파일이 없거나 망가졌고 임시 파일이 온전하면 되살린다. 반쯤 쓴 임시 파일은 되살리지 않는다
- 되살리기가 실패해도 임시 파일이 남고, 막힌 것이 풀리면 다음에 되살린다. 메모리 창구와 진짜 파일 둘 다 본다
- 되살리지 못한 사이에도 그 런을 읽고, 메타의 런 있음 을 내리지 않고, 새로 쓰려 하면 덮지 않고 실패를 알린다
- 진짜 파일 창구가 기존 파일을 바꿔 달고 임시 파일을 남기지 않는다. 임시 폴더에 실제로 써 본다
- 런 종료 기록 쓰기가 실패하면 런 파일과 메모리의 런이 남고, 메타는 되돌아가며, 저장 알림 대신 쓰기 실패 팝업이 뜬다.
  다시 끝내면 기록이 한 번만 쌓인다
- 기록을 쓰고 런 파일을 지우기 전에 꺼진 모양에서 프로필을 고르면 파일이 지워지고 메모리에도 런이 없고 이어하기가 꺼진다
- 백업만 남은 프로필이 원래 이름으로 목록에 나오고 본 파일이 되살아나며 팝업이 뜬다. 첫 프로필 만들기가 덮지 않는다
- 망가진 본 메타를 백업으로 되살리면 런을 이어 붙여 런이 남는다. 이미 기록된 런은 붙이지 않고 지운다.
  본 메타를 끝내 못 읽으면 백업과 런이 온전할 때만 되살린다. 이어하기에서 메타를 못 읽으면 타이틀은 읽지 못함이다
- 본 메타가 망가졌는데 런을 못 읽으면 백업을 확정하지 않고, 런이 읽히면 되살려 런이 남는다. 읽지 못하는 임시 메타만 남은 프로필은 읽지 못한 칸이다.
  예전 런을 불러오거나 버린 다음 런이 새 번호를 받는다
- 런 번호는 시작할 때 매기고 버린 런 다음 런이 새 번호를 받는다. 날이 바뀐 뒤 런을 저장하면 마지막 플레이 날짜가 오늘이 되고,
  런을 하다 나간 프로필이 게임을 켤 때 골라진다

## 기획서에 없어 내가 정한 부분

- **현재 방을 노드 번호로 적는다.** 위에 적었다
- **체크섬 방식.** 기획서는 "검사하는 값"이라고만 했다. FNV-1a 를 골랐다
- **지난 런 기록 스무 개.** 기획서는 개수를 정하지 않았다. 설정 에셋에서 바꾼다
- **런 번호.** 메타의 런 횟수(`RunCount`)를 **런을 시작할 때** 올리고 그 값을 번호로 쓴다.
  새 게임으로 버린 런 다음 런도 새 번호를 받는다. 2026년 10월 9일 원재가 "시작 시가 맞다" 고 정했다.
  바꾸기 전에 시작한 런은 불러올 때, 버릴 때, 끝낼 때 런 횟수를 그 번호까지 맞춘다. 그래야 다음 런이 같은 번호를 받지 않는다
- **마지막 플레이 날짜.** 런 데이터를 저장할 때마다(런 시작, 방 진입, 방 완료, 스테이지 넘김, 저장하고 나가기, 보상 받기)
  오늘 날짜로 맞춘다. 날짜가 바뀐 경우에만 메타를 다시 쓴다. 2026년 10월 9일 원재가 정했다.
  날짜를 주는 곳은 `SaveService.Today` 이고 비워 두면 기기 시계다
- **최대 체력 99.** 전투 시스템이 정할 값이다. 그때까지 설정 에셋에 둔다

- **도감.** `DiscoveredIds` 에 담을 자리만 있다
